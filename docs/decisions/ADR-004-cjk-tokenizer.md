# ADR-004: 自实现 CJK 单字+双字切分，不引入 jieba

## Status

Accepted（2026-09-21）

## Background

`rank_bm25` 默认的 tokenizer 是 `text.split()`——按空白切分。
中文没有空格，整句话会变成一个 token，于是：

- 检索任何中文词都命中不了（除非整句完全相同）
- 语料里每个"词"都是唯一的，IDF 失去意义
- 这是静默失效：程序不报错，检索恒返回空或噪声

主流解法是引入 `jieba`。实测在本机环境（Windows + Python 3.13）：
`jieba` 只发布源码包（sdist），安装时需要编译；而本机没有 MSVC 构建工具链。

但更重要的理由是它违反 ADR-002 的约束：**向量检索可以离线降级，词法检索不能**。
离线档里词法是唯一有效的检索通路，如果它依赖一个需要编译的包，
"干净环境一键复现"就退化成"先装好编译器"。

## Decision

在**契约层**（`contracts/text.py`）实现一个零依赖的 CJK 切分函数：

```python
def tokenize(text: str) -> list[str]:
    # 1. 拉丁词按 [A-Za-z0-9_]+ 切分，去英文停用词
    # 2. 连续汉字段切出「单字」+「相邻双字」
    #    例：'契约层' -> ['契', '约', '层', '契约', '约层']
```

放在契约层而不是 `providers/bm25_index.py`，是因为**检索与护栏必须共用同一套分词**：
护栏靠词法重合度判断"引用是否成立"，如果两边分词规则不同，
会出现"检索召回了，护栏却说没有依据"这类极难排查的不一致。

中文停用词用一个小集合手工列出（`的了是在和有与我你他她它们个之也就都而及与或很`）。

## Consequences

**正面**

- 零依赖、无编译、纯函数、确定性，可离线验证。
- 检索召回与护栏判据严格对齐。
- 单字 + 双字的切分对 BM25 已经够用：`契约层` 这类三字词会被
  `契约`、`约层` 两个双字覆盖，常见查询能命中。

**负面**

- **不是真正的分词。** `中国人民银行` 会被切成 `中国`、`国人`、`人民`、`民银`、`银行`
  ——`国人`、`民银` 是噪声词元，会带来少量假阳性匹配。
- 双字切分让倒排索引体积约为单字的两倍。
- 停用词表是手工维护的，可能不全。

缓解措施：

- 词法噪声由 RRF + 重排吸收——被误召回的块在重排阶段会被压下去。
- 在线档把 `dense_weight` 设为 1.0，语义通路承担主要召回责任。
- 需要精确短语匹配时，应上调 `dense_weight` 而不是指望词法通路。

**如果未来要换成 jieba**：只需改 `contracts/text.py` 里的 `tokenize()` 一个函数，
调用方（BM25 索引、护栏、记忆检索）全部无需改动。这正是把它放在契约层的收益。
