# ADR-009: 重排器的职责边界——重排，不筛除

## Status

Accepted（2026-09-21）

## Background

这是一条**真跑在线档时才暴露出来的**决策。

LLM 重排器的提示词要求模型"输出一个 JSON 数组，最多 top_n 个编号"。
实测中模型经常只返回**部分排序**——比如 9 条候选只回了 `[2]`。

初始实现的做法是：把模型提到的候选按顺序收下，直接返回。
结果：**9 条候选进，1 条候选出。**

后果是连锁的，而且每一环都不报错：

1. 检索结果从 9 条变成 1 条（`SearchOutcome.results` 静默变短）。
2. 那 1 条恰好不是回答问题所需的块（模型只是觉得它最相关）。
3. 智能体拿着 1 条无关材料去生成。
4. 护栏按 H4/S1 判定"论断缺乏依据"，拒答。
5. 用户看到的是"知识库中没有足够依据"——一个**与真实原因无关**的解释。

一个被定义为"锦上添花"的环节，把整条链路的召回打成了 1/N，
并且把故障伪装成了"知识库覆盖不足"。

## Decision

明确重排器的契约边界：**它只负责改变顺序，不负责决定哪些候选值得保留。**

实现上：

```python
picked = [候选中被模型提到的，按模型顺序]
rest   = [候选中被模型忽略的，按原相对顺序]
ranked = (picked + rest)[:top_n]
```

三条配套规则：

1. **模型返回空数组或全部越界时，退回原始顺序**，而不是返回空列表。
   "筛除"是护栏（ADR-007）的职责，不是重排器的。
2. `_fallback()` 在解析失败时同样返回 `items[:top_n]`——保召回，只丢顺序。
3. `SearchOutcome` 新增 `rerank_input` 字段，记录实际喂入重排器的条数。
   没有这个字段，上面那类故障在诊断时看不见。

## Consequences

**正面**

- 召回不会被重排环节意外压掉。不变量：`len(result) == min(len(candidates), top_n)`，
  已由 `tests/unit/test_llm_rerank.py::test_recall_is_never_worse_than_the_model_order`
  参数化覆盖。
- 部分排序仍然被采纳（头部顺序是对的），只是尾部不做判断——这符合实际信息量：
  模型给出 1 个编号，说明它只对第 1 名有把握。
- 模型输出的不完整性在 `health()` 里通过 `partial_order` 暴露，
  但不标记为 `degraded`——补齐是正常路径，不是故障。

**负面**

- 模型的"我认为这些都无关"这个判断被忽略了（因为会被补齐）。
  这是有意的：如果模型真的认为都无关，护栏的 `screen` 会用可复核的
  覆盖度判据做同样的事，比一个不可解释的 `[]` 更可靠。
- 重排的"过滤掉噪声"能力被削弱。需要过滤时应显式配置阈值，
  而不是默认交给模型。

**附带发现**：调试这一步时还发现 `rerank.top_n` 配置项**从未被读取**
（检索器固定传 `top_k`）。一个静默无效的配置项比没有这个配置项更糟，
因为它会让使用者以为自己调过参数了。现已接入，并新增
`rerank.candidates`（喂入条数）作为 LLM 重排的主要成本闸门——
30 条候选的提示词在 CPU 上要跑近一分钟，8–12 条即可。
