# ADR-005: 默认向量库用 numpy 精确检索，而非 HNSW

## Status

Accepted（2026-09-21）

## Background

向量检索的默认选择通常是向量数据库（Qdrant / Milvus / Chroma / FAISS），
用 HNSW 之类的近似最近邻（ANN）索引。

但 ANN 的前提是"暴力扫描太慢"。这个前提在本项目的实际规模下不成立：

- 本机实测：9 个块，1024 维，numpy 全量余弦耗时 < 1 ms。
- 即使到 10 000 个块 × 1024 维 = 约 40 MB 的 float32 矩阵，
  一次矩阵乘法在现代 CPU 上约 10–20 ms，仍在交互可接受范围内。
- 一个知识库系统在 10 000 块以下时，ANN 的构建开销和召回损失
  （HNSW 通常有 95–99% 召回）反而不划算。

同时引入向量数据库会带来一串新的运维面：服务部署、端口、集合管理、
连接池、版本兼容。这些都必须在"干净环境一键复现"里被处理，
而它们对当前要解决的问题没有直接贡献。

## Decision

默认向量库为 `NumpyVectorStore`：

- 全量 float32 矩阵常驻内存，检索用 `matrix @ query / (‖row‖·‖query‖)` 精确计算。
- 持久化用 `vectors.npy`（矩阵）+ `chunks.jsonl`（块），行序严格对应。
- **不引入任何向量数据库服务**。

同时保留 `QdrantVectorStore` 作为契约的第二个实现，
由 `vectorstore.provider` 一行配置切换，用于规模过万的场景。

## Consequences

**正面**

- 零外部服务，`uv sync` 之后立刻可跑，离线档完全自洽。
- **精确检索，召回率 100%**，没有"近似"这一层不确定性，评测指标干净。
- `tests/contract/` 可以用同一套断言验证 numpy 与 Qdrant 两个实现，
  证明"换向量库不改上层"是真的。
- 数据格式是裸 numpy 数组，可以用任何工具检查。

**负面**

- 内存占用与块数线性相关，10 万块 × 1024 维约 400 MB，之后不可接受。
- 每次 `upsert` 都重写整个 `.npy` 文件（`np.save` 不支持追加），
  大批量导入时是 O(N²) 的写入量。当前语料规模下无感，大规模导入需要分批。
- **无写锁**：多进程并发写入会互相覆盖。这是"单 worker 部署"这条约束的根源。
- 没有元数据过滤能力，只能按 `doc_id` 过滤。

**触发切换的条件**：块数超过 10 000，或需要多进程/多实例共享索引，
或需要元数据过滤。届时改 `vectorstore.provider = "qdrant"` 并部署 Qdrant 即可。
